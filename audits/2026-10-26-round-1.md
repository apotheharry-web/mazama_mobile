# Audit of `mazama_mobile/SIGN-IN-SECURITY.md` against the source

## Summary

I checked the nine claims against the Dart source, the bundled flow specs and the Android and iOS native code. I did not rely on the comments. The core guarantees hold in the code. The password can only be the entire value of a POST form field sent to an allowlisted host other than `psilocybin.oregon.gov`. Tokens are only sent to allowlisted hosts, and no request to Mazama's server carries one. Every flow request and redirect hop is checked against the allowlist. The host list needs a valid Ed25519 signature. Sign-in failure reports carry only fixed words. No `/p/` client sends a token or password. Three claims are only partly true:

- **Claim 5 (in-app sign-in page):** on Android, form POST navigations in the WebView never go through the navigation check. The "always" clearing of cookies before the page opens is also only best effort.
- **Claim 6 (scrubbing):** each flow only scrubs the values in its own context. The email is not scrubbed in state-read, renewal or browser-sign-in errors, and an old refresh token is not scrubbed once a rotated one has replaced it.
- **Claim 9 (storage):** the worker's email is also kept, in plain text, in `server_outbox.json` and `server_catch_up.json`, and signing out does not delete those files. The paragraph on desktop builds describes builds this repository does not contain.

Several other points should be disclosed:

- The flow interpreter's cookie jar is not scoped by host.
- Lab-report downloads follow redirects to any https host (without the token).
- A sign-in spec fetched from the server chooses the text of the questions put to the worker, and whether the answer is hidden.
- The README promises `.sig` files and a sync tool that this copy does not contain.

## Claim 1: The password goes only to the state's sign-in, as a form field of a POST — TRUE

**Evidence**
- The password enters at `mazama_mobile/lib/main.dart:843-849` (obscured `TextFormField`). It goes into `inputs` at `main.dart:541` and is passed to `_attempt` (`main.dart:550`, `580`). From there it goes to `attemptSignIn` (`main.dart:772-775`, `mazama_mobile/lib/sign_in_attempt.dart:24-30`), which calls `runFlow`. The claim's "passes it only to `runFlow`" skips the `attemptSignIn` hop, but the effect is the same.
- The demo check (`main.dart:56`, `533-536`) compares locally and returns before any client is made.
- The rule is `usableLoginSpec` (`mazama_mobile/lib/login_spec_store.dart:78-108`):
  - `_secretsPlaced` (`:176-215`). The password, and every `await_input` `into`, may only be the entire value of a form field of a `request` whose method is exactly `POST` and whose vars-filled host isn't `psilocybin.oregon.gov` (`_typedFormFields` `:148-157`, `urlHostForSecrets` `:120-130`). The scan covers all keys and values of `vars`, the flow names and every step (`_hasText` `:160-165`). No `when`, `json_var` or check `vars` may name the secret inputs (`:198-213`), and no var may be named `email`, `password` or `refresh_token` (`:177`).
  - `_plainMapsOk` (`:222-236`). `_setNamesOk` (`:259-271`, with the renew `refresh_token` exception at `:265`).
  - Templating is exactly `\{\{(\w+)\}\}` and is never re-scanned (`mazama_mobile/lib/flow/flow_spec.dart:16-26`), so `{{ password }}` is never filled.
- Where the rule runs:
  - The saved spec: `LoginSpecStore._saved` (`login_spec_store.dart:451-460`) and `save` (`:501-506`).
  - A fetched spec: `mazama_mobile/lib/login_spec_client.dart:94`, and again in `main.dart:569-575` before the retry.
  - The browser spec: `mazama_mobile/lib/browser_login_spec.dart:22-31`.
  - Debug "Try": `mazama_mobile/lib/debug_signin_files_page.dart:507`.
- The bundled `assets/flows/login.yaml` uses `{{password}}` only at `login.yaml:98`. That is the `self_asserted` POST to `{{b2c}}`, which is `https://oregonpsilocybinprodb2c.b2clogin.com/...` (`:22-24`, `:85-98`).
- The password is never stored: `Session.toJson` (`mazama_mobile/lib/session.dart:68-73`) has no password field. It is never logged: there is no `print` or `debugPrint` of it anywhere (see Method). On the server-link side, no `/p/` client takes a password parameter.
- A host added by a signed list could also receive the POST, as the claim says. Runtime host checks are at `flow/flow_runner.dart:920-923`.

**Caveats**
- The claim's "Search check" is inaccurate. `password` also appears in `lib/debug_signin_files_page.dart:501-523` and `:668-701` (the debug Try dialog). That page is covered only under "What these claims do not cover".
- A fetched spec chooses each `await_input` prompt and its `secret` flag (`flow_runner.dart:729-746`). The dialog title is the fixed text "The state is asking" (`lib/sign_in_prompt.dart:59-74`). So a server-chosen spec can say "re-enter your password" with `secret: false`. The answer is then shown in clear, with keyboard suggestions and autocorrect on (`sign_in_prompt.dart:70-72`), and it isn't added to the scrub keys. The rule still limits where it is posted.
- The rule restricts the `{{password}}` template text, not values read back from responses. If an allowed host ever echoed the posted password, a spec could capture it under another name and send it to any allowlisted host. This is theoretical; B2C isn't known to do so.

## Claim 2: Tokens go only to the allowlisted hosts — TRUE

**Evidence**
- Requests that carry a token, from the bundled specs:
  - `Authorization: Bearer {{access_token}}` appears only in `assets/flows/state_reads.yaml:57,82,107,132`, `sale.yaml:41` and `sb303.yaml:36,62`. All are on `{{site}}` = `https://psilocybin.oregon.gov/` (`state_reads.yaml:40-42`, `sale.yaml:28-30`, `sb303.yaml:21-23`).
  - The `refresh_token` form field appears only at `login.yaml:183` and `flows_phone/login_browser.yaml:146`, on `{{b2c}}`.
  - `sb303.yaml` isn't referenced anywhere in `lib/`.
- All of these run through `runFlow` with `allowedHosts: currentAllowedHosts()`:
  - State reads: `lib/state_client.dart:72-73`.
  - Sale: `lib/cart_page.dart:1771-1772` and `2407-2408` (spec loaded from the bundle only, `cart_page.dart:438`).
  - Renew: `lib/session.dart:209-210`.
- `currentAllowedHosts()` is the built-in two plus a verified list's hosts (`lib/login_hosts_store.dart:102-103`, `135`).
- `downloadStateDocument` (`lib/state_document_client.dart:46-125`):
  - It refuses a non-allowed API host (`:62-64`).
  - It sets `followRedirects = false` (`:71`).
  - It adds `Authorization` only when `sameOrigin` (same scheme, host and port, `:66`, `:75`).
- Flow redirects drop `Authorization` when the authority changes (`flow_runner.dart:855-867`).
- Every `/p/` client uses only `appApiKeyHeaders` plus a content type, and none takes a token parameter. Checked: `sale_log_client.dart:61-70`, `sale_failure_client.dart:55-64`, `order_client.dart:81-88`, `par_client.dart:77-80`, `inventory_upload_client.dart:58-62`, `scan_match_client.dart:113-121`, `coa_data_client.dart:103,151,210-219`, `signin_failure_client.dart:104-115`, `login_spec_client.dart:76`, `login_hosts_client.dart:49`, `packages_client.dart:251`, `label_client.dart:34`, `center_status_client.dart:100`, `sheets_client.dart:163`, `mazama_inventory_client.dart:132`, `ping_client.dart:36`.
- `CatchUpAuth` holds the access token only in memory and only passes it to the state calls (`lib/catch_up_store.dart:137-142`, `lib/server_link.dart:197-217`).
- `configured_coa_submit.dart:72-96` sends exactly what the claim lists to `uploadCoaParse`.

**Caveats**
- The flow cookie jar is not scoped by host (`flow_runner.dart:286-301`, `686`, `928-929`, `864-865`). Every cookie set during a run is sent on every request of that run. During `login` that means the B2C SSO and session cookies (credential-like) also go to `psilocybin.oregon.gov`, and to any list-added host. The file comment (`flow_runner.dart:12-13`) says so, but `SIGN-IN-SECURITY.md` doesn't.
- A fetched login or renew spec may place tokens in any header, query or form field on any allowlisted host. This is within the claim, but it is broader than "today, the state's".

## Claim 3: Every request the flows make is held to the allowlist, redirects included — TRUE

**Evidence**
- `defaultAllowedHosts` is exactly the two hosts (`lib/flow/flow_spec.dart:73`).
- `hostAllowedUrl` (`flow_spec.dart:83-104`): https only, port 443 only, no `\` and no `@`, a strict host grammar, and exact matches.
- `_runRequest` checks the URL as written and after `params` are added (`flow_runner.dart:920-923`), and builds `http.Request` with `followRedirects = false` (`:925`).
- The redirect loop (`:942-962`) follows only `redirectRules` (GET and HEAD, 301/302/303/307/308, `:812-821`), at most 10 hops (`:810`). Each hop is checked by `_nextHop` (`:835-840`) and rebuilt with `followRedirects = false` (`:856`).
- `open_browser` start and `until` URLs are also checked (`:763-773`).

**Caveat**
- This covers flows only. The hand-built lab-report download follows redirects to any https host (`state_document_client.dart:94-98`), without the token but with `Referer`, `Origin` and `User-Agent`. The webview's own traffic (claim 5) isn't covered either.

## Claim 4: Mazama's server is trusted for sign-in only within these rules — TRUE

**Evidence**
- Fetches happen only after a failure:
  - Password sign-in: after any failure other than `credentials` or `cancelled` (`main.dart:551-575`).
  - Browser sign-in: after any failure (`main.dart:712-727`).
- A fetched spec must be usable under the retry's hosts and newer than the one that failed (`main.dart:568-575`, `721-727`).
- The host list:
  - `verifiedHostList` (`login_hosts_store.dart:90-98`) is the only constructor (`HostList._`, `:81`).
  - `verifySigned` (`lib/signing.dart:91-104`) does strict base64 and an S < L check.
  - A list only adds hosts (`login_hosts_store.dart:102-103`).
  - A saved list is verified again on load (`:153-165`) and saved only after a session (`main.dart:626-632`).
- The bundled key `assets/signing/signing.pub` decodes to 32 bytes (checked locally), so it isn't `none`.
- Any signed list beats no list (`newerHostList` uses `compareSpecVersions(x, null) = 1`, `login_hosts_store.dart:113`; `flow_spec.dart:126-132`). Added hosts are named only afterwards (`main.dart:641-650`, `589`, `735`).

**Caveats**
- A fetched sign-in spec is **not** signature-checked on the phone, only rule-checked. Mazama's server (or anyone who can answer as it) chooses its steps, its question texts, where on allowlisted hosts the email and tokens go, and which client id or B2C policy the webview opens.
- I can't verify the claim that the key is copied "from the repository's shared `mazama_modules/flows/signing.pub` by `tool/sync_flows.sh`". Neither file is in this repository.
- The `.sig` files that the root `README.md` lists next to `login.yaml`, `login_browser.yaml` and `hosts.json` are absent, so the published `hosts.json` can't be checked against the key.

## Claim 5: Signing in on the state's own page — PARTLY TRUE

**Evidence for**
- JavaScript is on (`lib/browser_sign_in_page.dart:163`).
- No `runJavaScript`, `runJavaScriptReturningResult`, `addJavaScriptChannel`, `JavaScriptChannel` or `setOnConsoleMessage` anywhere in `lib/` (grep).
- The navigation rule is `decideBrowserNavigation` (`:75-80`): `until` first, frames always allowed, main frame held to the allowlist.
- The delegate is wired at `:164-200` and `238-251`. Only URLs are read (`onPageStarted`, `onUrlChange` and `onNavigationRequest` compare against `until`), and the final URL is popped back (`:233-236`).
- The code is exchanged by the spec's `token` step (`flows_phone/login_browser.yaml:108-134`).
- Clearing (`:224-228`) uses `clearCookies`, `clearCache` and `clearLocalStorage`. It runs before load (`:205-209`) and in `dispose` (`:262-266`).
- The inventory portal is a second, unrestricted, JS-enabled webview (`lib/inventory_portal_page.dart:12`, `29-56`), as the claim says.

**Why only partly**
- "Only main-frame navigations to allowed hosts load" isn't fully enforced on Android. Android's `WebViewClient.shouldOverrideUrlLoading` (which backs `onNavigationRequest` in `webview_flutter_android`) is not called for POST requests. So a form POST from the page, or from script in it, to any host loads unchecked. That is platform behaviour; the code doesn't compensate, and the file comment (`:20-26`) mentions only frames and the first `loadRequest`.
- "Cleared before the page opens (always)": `clearSignInBrowserData` swallows every failure (`:84-92`), and `_start` loads the page regardless (`:205-209`). The clearing before load is attempted every time but not guaranteed. The file comment calls it "the guarantee" (`:31-32`).
- `clearLocalStorage` may not cover every kind of site data (IndexedDB, service workers) on every platform. This depends on the plugin, and I didn't verify it.

## Claim 6: Secrets are scrubbed from error messages — PARTLY TRUE

**Evidence for**
- `defaultSecretKeys` (`flow_runner.dart:28`). `_scrub` is case-insensitive and exact-value (`:144-152`).
- Scrubbing is applied by `_fail` (`:197-205`) to every check, transport and `_blocked` message, and to prompts (`:739`). Secret `await_input` answers are added to the keys (`:699`).
- `_runOpenBrowser` never puts the returned URL in an error (`:778-790`). The bundled browser spec's errors don't name `code` (`flows_phone/login_browser.yaml:87,98,106,124,134`).
- `sessionFailureReportText` (`session.dart:158-163`) is used for every session failure sent to the server (`cart_page.dart:1828`, `1840`, `2421`, `2427`), and never `e.message`.

**Why only partly**
- Only values present in that run's `ctx` are scrubbed.
  - The browser sign-in runs with no inputs (`main.dart:710`, `730`), and renew and state reads get no email (`session.dart:209`, `state_client.dart:72`). So an email the state echoes in those flows' errors isn't replaced. Those errors are shown on screen: `main.dart:505-515`, `SessionExpired` messages at `cart_page.dart:1831`, `869`.
  - In renew, the extracted rotated `refresh_token` overwrites the input one (`flow_runner.dart:653`, `login.yaml:191`). A later `then_require` message holding the old token wouldn't be scrubbed.
  - Non-secret `await_input` answers are never scrubbed.
- These messages stay on the phone (they aren't sent to the server), so the impact is low, but "every exact copy of ... the email" is overstated.
- Some error paths don't use `_fail`: `FlowError('no such flow: …')` and the `timeout_seconds` error at `flow_runner.dart:85`. They contain only spec text.

## Claim 9: Where credentials and tokens are stored — PARTLY TRUE

**Evidence for**
- `session.json` is written in plain text by `SessionStore.save` (`lib/session_store.dart:68-77`), in `getApplicationSupportDirectory()` (`:25-27`).
- The fields are those in `Session.toJson` (`session.dart:68-73`). No other file holds a token.
- Android: `allowBackup="false"` and `fullBackupContent="false"`, plus `dataExtractionRules` (`android/app/src/main/AndroidManifest.xml:13-15`). The rules exclude every domain for cloud backup and device transfer (`android/app/src/main/res/xml/data_extraction_rules.xml`).
- iOS: `excludeAppSupportFromBackup` runs at launch (`ios/Runner/AppDelegate.swift:16`, `32-38`), with `try?`, so best effort.
- Debug page: `lib/debug_local_storage_page.dart:66-74` shows the email and expiry and whether tokens are present, not the tokens themselves. It is reachable only behind `kDebugMode` (`lib/select_center_page.dart:463`).

**Why only partly**
- The email, which the document's own Definitions count as a credential, is also stored in plain text in other files:
  - `server_outbox.json`: `lib/server_outbox.dart:110-118`, `173`.
  - `server_catch_up.json`: `lib/catch_up_store.dart:70-76`, `103`.
  - The reconciliation PNG left in the temp folder: `reconcile_page.dart:135-137`.
- Signing out (`goToSignIn`, `main.dart:58-68`) deletes only `session.json`, so the email outlives the session.
- These files sit in the same backup-excluded folder, except the PNG, which is in the temp/cache folder.
- "Desktop builds (Linux, Windows) … macOS": this repository has only `android/` and `ios/`, and the root `README.md` says "Only the Android and iOS apps are built (no desktop or web folders)". The paragraph describes code paths (`session_store.dart:45-58`) of builds that aren't published.

## Other findings

**Things that send or expose user data and aren't in the claims**
1. **Unscoped cookie jar.** Sign-in cookies (including B2C SSO cookies) go to every host a run touches, including list-added hosts (`flow_runner.dart:12-13`, `286-301`, `928-929`). Fix: key the jar by host.
2. **Lab-report download redirects.** These go to any https host, unchecked against the allowlist (`state_document_client.dart:94-98`). The token is dropped, but `Referer`, `Origin` and `User-Agent` are sent. Fix: check each hop with `hostAllowedUrl`.
3. **Server-chosen worker prompts.** A fetched sign-in spec sets the prompt text and the `secret` flag of questions shown under "The state is asking" (`sign_in_prompt.dart:59-74`, `flow_runner.dart:729-746`). Fix: require `secret: true` in `usableLoginSpec`.
4. **Android WebView POST navigations** bypass the main-frame allowlist (see claim 5).
5. **Email persists after sign-out** in the outbox and catch-up files (see claim 9). Leftover label photos (`TextScanner.kt:74`, never deleted) and reconciliation PNGs (with the email) stay in cache.
6. **iOS widget data.** The App Group `UserDefaults` used by the cart-timers widget (`ios/Runner/CartTimerWidget.swift:22-36`) holds cart names and timers outside Application Support, so the backup exclusion doesn't cover it. It holds no credentials.

**Inaccuracies in the claims document, the README and comments**
1. Claim 1's search check misses `lib/debug_signin_files_page.dart`. Claim 1 also says `_attempt` passes the password to `runFlow`; it goes through `attemptSignIn` first.
2. Claim 2 cites `sb303.yaml`, which the app never loads.
3. Claim 5 says the clearing before load happens "always"; it is best effort.
4. Claim 6 overstates scrubbing of the email (see above).
5. Claim 9's desktop paragraph contradicts the README.
6. Claim 4 relies on `tool/sync_flows.sh` and `mazama_modules/flows/signing.pub`, and the README lists `.sig` files. None of these are in this repository.
7. "Known gaps" says `build.gradle.kts` refuses a release build without the upload key, but `MAZAMA_DEV_RELEASE=1` allows a debug-signed release build (`android/app/build.gradle.kts:44-50`).
8. "Known gaps" says flow errors are scrubbed and only `cart_page.dart`'s unexpected-exception text isn't. Other unscrubbed texts also go to the device log: server error text and file errors at `cart_page.dart:1898`, `1917`, `server_outbox.dart:273`, `catch_up_store.dart:192`, `cart_page.dart:2438`.
9. A stale comment in `lib/signing.dart:79` and `:8-9` says the key is `none`.

**"What these claims do not cover": anything missing**
- The phone doesn't verify signatures on fetched sign-in specs; a reader may assume SL-D14 signing applies on the phone.
- Server-chosen prompts to the worker (finding 3).
- The unscoped cookie jar (finding 1).
- The Contact sheet links (`lib/mazama_contact.dart:8-15`: signal.me, mailto, and a URL with embedded guest credentials). Only the guest login is mentioned, under Known gaps.
- Android's POST-navigation gap.

The listed items themselves (unreproducible builds, the state, the server code, key custody, no certificate pinning, the debug page, server-chosen links, the open-source link) are accurate. On pinning: there is no `badCertificateCallback`, `SecurityContext` or `HttpOverrides` anywhere in `lib/`.
