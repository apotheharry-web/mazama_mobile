# Audit of `mazama_mobile/SIGN-IN-SECURITY.md` against the source

## Summary

I checked all nine claims against the Dart, YAML, Kotlin, Swift and build files in this copy, without running anything. The core promise holds in the code. The password typed into the app's own form reaches only `runFlow`, and the spec rule only lets it be posted as a whole form field to an allowlisted host other than `psilocybin.oregon.gov`. The access and refresh tokens go only to allowlisted hosts. Every flow request and redirect hop is checked against the allowlist before it is sent. Host lists are Ed25519-verified against the bundled key. No `/p/` request carries a token. The webview gets no injected JavaScript. Seven claims are TRUE as worded, with caveats on 1, 5, 7, 8 and 9. Claim 6 (scrubbing) is PARTLY TRUE for three reasons. First, one interpreter error message is built without `_scrub`. Second, scrubbing works by key name, so a token a spec reads under another name is not scrubbed. Third, the claim says flow errors are "shown only on the phone", but the sale flow's error text is sent to Mazama's server, as claim 7 itself says. The root `README.md` has one clear inaccuracy: it says the app uses the signed `login.yaml`/`login_browser.yaml` only when their signature verifies, but the phone never checks a signature on a sign-in spec. The README also points to an `AUDIT.md` that is not in this copy. Some things a careful reader should be told are covered nowhere: OS autofill and keyboards, the external camera app on Android, connection metadata, and the device id that links sign-in failure reports to a worker.

## Per claim

### 1. The password goes only to the state's sign-in (TRUE)

Evidence:
- Entry point. `mazama_mobile/lib/main.dart:541` puts the password into the `inputs` map. That map is passed only to `_attempt` (`main.dart:550`, `:580`), then `attemptSignIn`, then `runFlow` (`mazama_mobile/lib/sign_in_attempt.dart:30`).
- The only other use is `isDemoSignIn` (`main.dart:56`, `:533`), which is checked locally. The field is obscured (`main.dart:846`). The debug-only "Try" dialog (`mazama_mobile/lib/debug_signin_files_page.dart:501-524`) uses the same `attemptSignIn`. It is reachable only behind `kDebugMode` (`mazama_mobile/lib/select_center_page.dart:463`).
- Storage. `mazama_mobile/lib/session.dart:68-73` has no password field. A repo-wide grep finds `password` in `lib/` only in the places the claim lists.
- The rule, in `mazama_mobile/lib/login_spec_store.dart`:
  - `_typedFormFields` (`:148-157`) allows `{{password}}` only as the entire form value of a request whose `method` is exactly `POST`, to a host other than `psilocybin.oregon.gov`. The host is read after the vars are filled in, lower-cased, with port and trailing dot stripped (`:120-130`).
  - `_secretsPlaced` (`:176-215`) scans vars, flow names and every key and value of every step, and refuses `when` or `json_var` on the secret inputs and check `vars` naming typed values.
  - `_plainMapsOk` (`:222-236`) requires plain-text params, headers and form, with no `{{` in keys.
  - `_setNamesOk` (`:259-271`) blocks overwriting vars and inputs, except renew's `refresh_token` extract.
  - It is applied to saved specs (`:454`, `:502`), fetched specs (`mazama_mobile/lib/login_spec_client.dart:94`, again at `main.dart:568-575` before the retry) and the browser spec (`mazama_mobile/lib/browser_login_spec.dart:135`).
- Templates. `{{name}}` is `\{\{(\w+)\}\}` only (`mazama_mobile/lib/flow/flow_spec.dart:16`).
- Sending. The form becomes `req.bodyFields` (`mazama_mobile/lib/flow/flow_runner.dart:931-932`). A POST's 3xx is never followed (`flow_runner.dart:820-821`, `:948`), so the password cannot be re-sent to another host.
- Bundled spec. `mazama_mobile/assets/flows/login.yaml:85-98`: `{{password}}` appears only in `self_asserted`, a POST to `{{b2c}}` (the state's B2C tenant).
- Display. Errors pass through `_scrub` (`flow_runner.dart:144-152`, `:203`). `await_input` prompts are scrubbed (`flow_runner.dart:739`).

Caveats:
- The claim is about the app's code. The password field is a normal Flutter `TextFormField` with autofill left at its default (`main.dart:843-850`). The OS password manager or autofill service, and a third-party keyboard, can still see, save or sync what is typed. Neither claim 1 nor "What these claims do not cover" says so.
- As stated, a host added by a signed list can receive the POST.

### 2. Tokens go only to the allowlisted hosts (TRUE)

Evidence:
- Every `Authorization: Bearer {{access_token}}` is in steps on `{{api}}`/`{{site}}` = `https://psilocybin.oregon.gov/...`: `mazama_mobile/assets/flows/state_reads.yaml:55-57` (and the other read flows), `mazama_mobile/assets/flows/sale.yaml:39-41`, and `sb303.yaml:34-36`, which nothing in `lib/` loads.
- `refresh_token` appears as a form field only in renew steps to `{{b2c}}` (`login.yaml:173-183`, `login_browser.yaml:136-146`).
- The token reaches flows only through `runFlow` with `allowedHosts: currentAllowedHosts()`:
  - `mazama_mobile/lib/state_client.dart:197-198`
  - `mazama_mobile/lib/cart_page.dart:1771`, `:2407`
  - `session.dart:209-210`
- The one hand-built request is `mazama_mobile/lib/state_document_client.dart`. It refuses a non-allowlisted start (`:62-64`), sends the `Authorization` header only when scheme, host and port all match the start (`:66`, `:75`), and refuses to follow a redirect to non-https (`:94-97`).
- Flow redirects drop `Authorization` across hosts (`flow_runner.dart:857`, `:861`).
- Every `/p/` client sends only `appApiKeyHeaders` and the JSON bodies listed under claim 7. None contains a token (for example `mazama_mobile/lib/sale_log_client.dart:64-69`, `mazama_mobile/lib/coa_data_client.dart:212-222`). `Bearer` occurs once in `lib/` (`state_document_client.dart:75`).
- The cookie jar is per run and not per host (`flow_runner.dart:686`, `:929`, `:864-865`), as disclosed.

Caveats:
- `CatchUpAuth` holds the access token in memory only (`mazama_mobile/lib/catch_up_store.dart:137-142`). It is used for state reads, never written to `server_catch_up.json` (`catch_up_store.dart:125-133`).
- The authorization code (part of the doc's "Tokens" definition) goes only to the B2C token endpoint (`login.yaml:145-156`, `login_browser.yaml:108-119`). In the browser path it is never loaded: the navigation is stopped at `until` (`mazama_mobile/lib/browser_sign_in_page.dart:79`, `:249-251`).

### 3. Every flow request is held to the allowlist, redirects included (TRUE)

Evidence:
- `defaultAllowedHosts` is two exact hosts (`flow_spec.dart:73`).
- `hostAllowedUrl` (`flow_spec.dart:83-104`) requires https, refuses `\` and `@`, accepts no port other than 443, and matches the host's shape exactly.
- In `_runRequest`, the raw URL is checked before `Uri.parse` and the built URL is checked again (`flow_runner.dart:920-923`). The request is made with `followRedirects = false` (`:925`).
- Hops are rebuilt by `_hopRequest`, also with `followRedirects = false` (`:856`). Each hop is checked by `_nextHop` before it is sent, including scheme-relative and absolute forms (`:835-840`, `:955-960`).
- Only GET and HEAD are followed, at most 10 hops (`:810-821`).
- The `open_browser` start URL and `until` are checked before the webview opens (`:763-773`).
- A blocked URL is never sent (`_blocked` throws before `_sendHop`).

Caveat: the documented exception, `downloadStateDocument`, follows a redirect to any https host carrying `Referer`, `Origin` and `User-Agent` (`state_document_client.dart:70-74`, `:94-98`). That matches the claim's own "Not covered" note.

### 4. Mazama's server is trusted for sign-in only within these rules (TRUE)

Evidence:
- Fetched specs: the reply is held to `usableLoginSpec` under the attempt's hosts and served mode, and its `specVersion` must match (`login_spec_client.dart:94-96`). It is re-checked in `main.dart:568-575` and `:721-723`. It is used only if newer. There is no signature check on the phone.
- Host lists:
  - `fetchLoginHosts` verifies and checks the version (`mazama_mobile/lib/login_hosts_client.dart:219-220`).
  - `verifySigned` uses strict base64, refuses `none`, checks S < L and runs Ed25519 (`mazama_mobile/lib/signing.dart:245-277`).
  - `HostList` has only a private constructor (`mazama_mobile/lib/login_hosts_store.dart:81`).
  - A list only adds hosts (`login_hosts_store.dart:102-103`).
  - A saved list is verified again on load (`login_hosts_store.dart:153-165`).
- `mazama_mobile/assets/signing/signing.pub` is a 32-byte base64 key, not `none`.
- "Can't be withdrawn": `newerHostList(candidate, null)` is always true (`login_hosts_store.dart:113`, `flow_spec.dart:126-132`).
- New hosts are named only after the sign-in (`main.dart:641-649`), or under a failed retry (`main.dart:589`, `:856-858`).

Caveat: the fetched spec, once saved, is also used for every later renewal (`main.dart:601`, then `SelectCenterPage`, then `ensureFreshSession`). So the server's choice of steps also governs where on the allowed hosts the refresh token goes from then on. That is within "where on the allowed hosts the email and tokens go", but worth knowing.

### 5. Signing in on the state's own page: the app does not read what the worker types (TRUE)

Evidence:
- `grep` finds no `runJavaScript`, `addJavaScriptChannel` or `JavaScriptChannel` in `lib/`. The only JavaScript-related calls are `setJavaScriptMode(unrestricted)` (`browser_sign_in_page.dart:165`, `mazama_mobile/lib/inventory_portal_page.dart:30`).
- The rule is `decideBrowserNavigation` (`browser_sign_in_page.dart:77-82`): `until` first; then frames load; then main frames must pass `hostAllowedUrl`.
- The delegate's callbacks read URLs only to detect `until` (`browser_sign_in_page.dart:166-202`, `:232`, `:240-253`). Nothing from the page is stored or shown.
- Clearing runs before load (`:207-211`, `:226-230`: `clearCookies`, `clearCache`, `clearLocalStorage`, failures ignored) and in `dispose`, best effort (`:264-268`).
- The inventory portal is a separate `WebViewController` with JavaScript on and no navigation filter (`inventory_portal_page.dart:29-56`), as disclosed.

Caveats:
- "Cookies and site data are cleared" covers, in code, cookies, the cache and localStorage only. Whether IndexedDB, sessionStorage or service workers are cleared depends on the plugin (`webview_flutter_*`), which is not in this copy and could not be checked.
- Likewise, which navigations Android and iOS route through `onNavigationRequest` (POSTs, `target=_blank`, frames) can only be confirmed on devices. The claim's own platform caveats are consistent with the file comment (`browser_sign_in_page.dart:20-27`).

### 6. Secrets are scrubbed from error messages (PARTLY TRUE)

What holds:
- `_scrub` (`flow_runner.dart:144-152`) replaces each value of `password`, `email`, `access_token` and `refresh_token` (`:28`), plus secret `await_input` answers (`:683`, `:699`), case-insensitively.
- `_fail` scrubs after templating (`:197-205`), and `_blocked` goes through `_fail` (`:826-828`).
- `_runOpenBrowser` never puts the returned URL in an error (`:778-791`).
- `sessionFailureReportText` gives fixed texts (`session.dart:158-163`). The cart uses it for session failures (`cart_page.dart:1828`, `:1840`, `:2421`, `:2427`).

What doesn't hold:
- **One FlowError built from a spec value skips `_scrub`.** `flowRequestTimeout` throws `FlowError('timeout_seconds must be a positive number of seconds, not $raw')` (`flow_runner.dart:80-88`). It reads `ctx['timeout_seconds']` at every request (`:939`).
  - `usableLoginSpec` checks only a *var* named `timeout_seconds` (`login_spec_store.dart:99`).
  - `_setNamesOk` lets a step `extract` into `timeout_seconds` when the spec declares no such var (`:259-271`).
  - So a fetched renew spec can extract the new access token into `timeout_seconds`, make a second request, and get the raw token into an error message. That message is shown on screen via `SessionSpecUnusable` (`session.dart:217`) and `goToSignIn(message: …)` (`cart_page.dart:1832`).
  - The claim's own pointer says `_scrub` is "used for every FlowError message built from a spec" (`SIGN-IN-SECURITY.md:206`); that is not true here.
- **Scrubbing is by key, not by value read.** The statement says every exact copy that the run "was given or read" is replaced. A spec can extract a token from a JSON answer under any other name (for example `tok`, without also extracting it as `access_token`) and template `{{tok}}` into an error. That copy is not scrubbed. The doc admits this only for the failed-sale report (claim 6 end, `session.dart:153-157`), not for on-screen messages.
- **"These messages are shown only on the phone (claim 7)"** (`SIGN-IN-SECURITY.md:199`) is not true for the sale flow, which is a state flow. Its FlowError message is sent to Mazama's server as the failed-sale reason (`cart_page.dart:1857`, `:2433`; `mazama_mobile/lib/sale_failure_client.dart:58-61`), as claim 7 itself says. The bundled sale spec can't embed the token (it is scrubbed), but the sentence is inaccurate.

Impact: the first two paths only show a value on the phone that the phone already holds, and only with a fetched or saved spec. Both are bounded by claim 4's trust in Mazama's server.

### 7. What the app does send to Mazama's server (TRUE)

Evidence (`mazama_mobile/lib/api_contract.g.dart:3`, `:7-43` for the routes):
- Sale log: `sale_log_client.dart:64-69` (email, device id, records, the state's reply).
- Failed sale: `sale_failure_client.dart:58-62`.
- Orders: `mazama_mobile/lib/order_client.dart:83-87` (email, device id, lines, free-text note).
- Par levels: `mazama_mobile/lib/par_client.dart:80`.
- Inventory upload: `mazama_mobile/lib/inventory_upload_client.dart:61` (the state's raw records).
- Scan match: `mazama_mobile/lib/scan_match_client.dart:116-123` (scanned lines, `typed`).
- Lab-report submission: `coa_data_client.dart:210-222` (PDF, guid, doc id, email, device id, state psilocybin).
- Lab-data batch lookup (lot guids): `coa_data_client.dart:151-152`.
- Sign-in failure reports:
  - The body is `mazama_mobile/lib/signin_failure_client.dart:107-114`.
  - Fixed words come from `reportedSigninStep` and `reportedSigninReason` (`signin_failure_client.dart:26-33`) and `bundledSigninStepIds` (`:38-55`).
  - Not sent for `credentials` or `cancelled` (`main.dart:554-557`, `:587`). Never sent from the browser path (`main.dart:682-756` has no `_reportFailure`).
- Failed-sale reasons: fixed texts for session problems; otherwise the sale flow's message or `unexpected <type>` (`cart_page.dart:1783-1786`, `:1857`, `:1872`). Bulk sales prefix `[bulk k of n]` (`:2388`).
- The install id is random (`mazama_mobile/lib/device_id.dart:20-27`).

Caveats:
- The list does not name the lot-guid batch lookup or the free-text order note.
- Inventory records and the state's sale reply are forwarded unfiltered, whatever fields the state includes.
- Every `/p/` call (including the `/p/ping` probe, `mazama_mobile/lib/ping_client.dart:36`) also gives the server the phone's IP address and timing.
- Sign-in failure reports carry no email, but they do carry the same install id that sale logs pair with the email. The server can link them to the worker.
- "Not sent for a wrong password" assumes the spec labels a wrong password `credentials`. A fetched spec can label it another way (fixed words still).

### 8. Third-party code (TRUE)

Evidence:
- Direct Dart dependencies (`mazama_mobile/pubspec.yaml:11-28`) match the list exactly.
- The `pubspec.lock` package set contains no analytics, ads, crash-reporting or Firebase package.
- The only native dependency added is `implementation("com.google.mlkit:text-recognition:16.0.0")` (`mazama_mobile/android/app/build.gradle.kts:103`). It is used in `mazama_mobile/android/app/src/main/kotlin/com/example/mazama_mobile/TextScanner.kt:104-120` and receives only the photo.
- iOS uses Vision (`mazama_mobile/ios/Runner/TextScanner.swift:15`).
- `pdfrx` opens PDFs only from memory (`mazama_mobile/lib/pdf_text.dart:161`).
- `share_plus` is used at `mazama_mobile/lib/reconcile_page.dart:139` (button "Save report", `:372`). In debug pages it is used at `debug_coa_label_page.dart:122` and `debug_adhoc_coa_diagnostics_page.dart:145`.

Caveats:
- On Android the label photo is taken by whatever **external camera app** answers `ACTION_IMAGE_CAPTURE` (`TextScanner.kt:74-80`). That app receives the image and may keep or upload its own copy.
- `pdfrx`'s PDFium is a prebuilt binary fetched at build time (comment at `pubspec.yaml:26-27`), not built from this source.
- `url_launcher`'s `inAppBrowserView` (Custom Tabs or SFSafariViewController) brings the system browser's own telemetry, much as the webview note says.

### 9. Where credentials and tokens are stored (TRUE)

Evidence:
- `mazama_mobile/lib/session_store.dart:26` uses `getApplicationSupportDirectory`. The file is `session.json` (`:68`), written as plain JSON (`:76`). Sign-out deletes only it (`:94-100`, `main.dart:60`).
- Android backup is off: `mazama_mobile/android/app/src/main/AndroidManifest.xml:13-15` and `mazama_mobile/android/app/src/main/res/xml/data_extraction_rules.xml:6-19`.
- iOS: `mazama_mobile/ios/Runner/AppDelegate.swift:16`, `:32-38` mark Application Support excluded from backup.
- The email is also stored in two other files:
  - `server_outbox.json` (`mazama_mobile/lib/server_outbox.dart:84`, `:114`, `:173`)
  - `server_catch_up.json` (`catch_up_store.dart:60-76`, `:103`)
- The reconciliation image goes to the temp folder (`reconcile_page.dart:135-137`). Scan photos go to `cacheDir` and are never deleted (`TextScanner.kt:74`).
- No other store writes the email or a token (the grep of `writeAs`/`File(` in Method).

Caveat: the claim doesn't mention the **webview's own cookie and website-data store**. It holds the state's B2C session cookies if the after-close clearing doesn't run (`browser_sign_in_page.dart:264-268`, best effort, as claim 5 says). It also holds the inventory portal's cookies. On iOS that store lives outside Application Support, so `excludeAppSupportFromBackup` does not cover it. Whether iOS backs it up could not be checked offline.

## Other findings

1. **The README misstates the signature check on sign-in specs.** `README.md:50` says of `login.yaml`, `login_browser.yaml`, `hosts.json`: "The app uses one only when its signature verifies against the key built into the app". That is true only for `hosts.json`. The phone never verifies a signature on a sign-in spec (`login_spec_client.dart:94-97` only runs `usableLoginSpec`), and claim 4 says so (`SIGN-IN-SECURITY.md:144-146`). Fix: say that only the host list is verified on the phone.
2. **The README's "one exception" understates claim 4.** `README.md:16-18` names only the signed host list. It doesn't say that Mazama's server can, without any signature the phone checks, change the sign-in steps and the wording of questions put to the worker, and choose where on the allowed hosts the email and tokens go. It also says the app names a new address "after using it" without saying that this is after the password has been posted there (which `SIGN-IN-SECURITY.md:152-154` does say).
3. **The README links a missing file.** `README.md:37-40` and `:52` point to `AUDIT.md` (the prompt and "the result of the last time we ran that audit"). No `AUDIT.md` is in this copy. The prompt is at the end of `mazama_mobile/SIGN-IN-SECURITY.md`.
4. **Unscrubbed interpreter error** (claim 6): `flow_runner.dart:85` embeds `ctx['timeout_seconds']` raw. One-line fix: build it with `_fail` or `_scrub`, or name no value.
5. **Claim 6 contradicts claim 7** on whether flow errors leave the phone (`SIGN-IN-SECURITY.md:199` vs `:225-228`).
6. **The Known-gaps `debugPrint` list is incomplete.** `mazama_mobile/lib/cart_timer_widget.dart:78` also logs a `PlatformException`'s text in release builds. The list names only `cart_page.dart`, `server_outbox.dart` and `catch_up_store.dart`.
7. **Not covered anywhere: OS and keyboard handling of typed credentials.** The OS autofill or password manager, and third-party keyboards, can save or sync the email and password typed into the app's form (`main.dart:831-850`), the `await_input` dialog (`mazama_mobile/lib/sign_in_prompt.dart:67-75`; non-secret answers keep autocorrect and suggestions on), or the state's page in the webview.
8. **The external camera app on Android** gets every label photo (`TextScanner.kt:77-80`). This is not mentioned in claims 8 or 9.
9. **Metadata and linkage.** Every `/p/` request and the `/p/ping` probe give Mazama's server the phone's IP and timing. The install id ties sign-in failure reports to the worker's emailed sale logs. Neither is stated.
10. **Unverified email in the browser sign-in.** The worker types an email that the state never checks (`main.dart:693`, `:710`: `inputs` is empty). It is stored in the session and sent to Mazama to attribute sales, orders and lab-report submissions. Anyone can type someone else's email. This is not a leak, but claim 7's "attributed to the worker who made them" implies more than the code checks.
11. **The debug signing key now carries the real app id.** `build.gradle.kts:39-51`, `:75`, `:98`: a `MAZAMA_DEV_RELEASE=1` test build is signed with the debug key under the real app id `com.mazamamushrooms.mobile`. So such a test build left on a phone has the same "debug key can sign an update" weakness that Known gaps describes for the old `com.example` builds. The doc mentions the debug key but not this.
12. **Verified accurate.** "Links Mazama's server chooses" (`mazama_mobile/lib/sheets_client.dart:114`, `mazama_mobile/lib/mazama_inventory_client.dart:57`: plain concatenation, so a path like `@other.host/` changes the host). The Contact sheet's guest login is in the URL (`mazama_mobile/lib/mazama_contact.dart:8`). The debug Sign-in files page fetches with no app key and saves only the address (`debug_signin_files_page.dart:81-91`, `:102-121`). All debug pages are behind `kDebugMode` (`select_center_page.dart:463`).
