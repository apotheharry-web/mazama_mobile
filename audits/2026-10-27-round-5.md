# Audit of `mazama_mobile/SIGN-IN-SECURITY.md` against the source

## Summary

I read every file and function the nine claims name, followed the password, email, access and refresh tokens and the authorization code from entry to every sink, ran the prescribed searches over `mazama_mobile/lib/`, and read the flow specs, the Android and iOS native code and settings, and the Rust reader's dependencies. Claims 1, 2, 3, 5, 6, 7, 8 and 9 hold as worded, within the limits they state. A few have small caveats, listed below. Claim 4 is only partly true. The interpreter's own guard (`neverRequest`) and the static check (`_noStateApiRequests`) do keep the app's own sign-in and renewal requests away from `psilocybin.oregon.gov` in every ordinary case. But the claim (and the README) says that "while any sign-in or renewal runs ... nothing is sent to that host", and three things contradict that:

- **The in-app browser is allowed to load that host.** During "Sign in on the state's page" the browser may load main-frame pages from `psilocybin.oregon.gov`, because it is on the allowlist. Frames, sub-resources and Android form posts are not checked at all. A fetched browser spec whose `until` differs from its `redirect_uri` can make the state's site load in full.
- **A redirect spelled with a trailing dot gets through.** The runtime check compares the raw `Uri.host`. A redirect to `psilocybin.oregon.gov.` passes the allowlist (which strips the dot) but not the `neverRequest` comparison (which doesn't), so it is followed.
- **A signed host list weakens the "never read or change records" sentence.** That sentence does not hold once a list adds a host: such a host receives the tokens, and whoever runs it can use them against the state's API from anywhere.

I also found no path that sends the password or a token to Mazama's server. The README's promise "never sent to Mazama or anyone else" is still stronger than the code can enforce, because whoever holds the signing key (kept on Mazama's server) can sign a host list that sends the password and tokens to a host of their choosing.

## Per claim

### Claim 1: TRUE

**Where the password enters and where it goes**
- It enters at `mazama_mobile/lib/main.dart:843-849` (an `obscureText` field). It is read only at `main.dart:533` (the demo check, `isDemoSignIn`, `main.dart:56`, which sends nothing) and `main.dart:541` (`inputs`).
- `inputs` goes only to `_attempt` (`main.dart:550`, and `main.dart:580` for the one retry with a fetched spec). `_attempt` calls `attemptSignIn` (`main.dart:772-775`), which calls `runFlow(spec, 'login', ...)` (`mazama_mobile/lib/sign_in_attempt.dart:32-33`).
- Inside `runFlow` it sits in `ctx` (`mazama_mobile/lib/flow/flow_runner.dart:688`) and leaves only through `_templateMap` into `params`/`headers`/`form` (`flow_runner.dart:915-917`, `985-988`), or through a check or error template (blocked by the rule below).

**The rule, for fetched and saved specs**
- `usableLoginSpec` (`mazama_mobile/lib/login_spec_store.dart:79-110`) runs `_noStateApiRequests` (`:96`), `_plainMapsOk` (`:97`), `_secretsPlaced` (`:98`) and `_setNamesOk` (`:99`).
- `_typedFormFields` (`:150-159`) allows `{{password}}` only as an entire `form` value, only when `method == 'POST'`, and only when the vars-filled host (`urlHostForSecrets`, `:122-132`, which lower-cases, drops the port and strips one trailing dot) is not `psilocybin.oregon.gov`.
- `_secretsPlaced` (`:194-233`) scans `vars`, the flow names, and every key and value of every step. It refuses `when`/`json_var` naming password, email or refresh_token, and refuses checks naming a typed name. `typedNames` (`:136-145`) adds every `await_input` `into`, and vars named email, password or refresh_token are refused (`:195`).
- `_plainMapsOk` (`:240-254`) requires plain-text values and no `{{` in keys. `_setNamesOk` (`:277-289`) blocks a step from overwriting a var or input, except renew's `refresh_token`.
- The template syntax is exactly `\{\{(\w+)\}\}` (`mazama_mobile/lib/flow/flow_spec.dart:16`). `when.equals` is never templated (`flow_runner.dart:503-513`), so it can't be used to slip `{{password}}` in either.

**Where the rule is applied**
- A saved spec: `LoginSpecStore._saved` (`login_spec_store.dart:469-478`) and `save` (`:519-524`).
- A fetched spec: `mazama_mobile/lib/login_spec_client.dart:94-97`, and again before the retry at `main.dart:569-575`. The spec that runs (`fetched.spec`, `main.dart:576`) is the object `usableLoginSpec` returned at `login_spec_client.dart:94`.
- The browser spec: `mazama_mobile/lib/browser_login_spec.dart:22-30`, and at `main.dart:721-723`.
- The debug "Try" button: `mazama_mobile/lib/debug_signin_files_page.dart:508-512`.

**Never sent elsewhere at run time**
- A POST is never followed on a redirect (`redirectRules`, `flow_runner.dart:826-827`; loop at `:956`).
- Every request is allowlist-checked (`flow_runner.dart:927`, `930`).
- The bundled `mazama_mobile/assets/flows/login.yaml:85-98` (`self_asserted`, POST to `{{b2c}}`) is the only use of `{{password}}`. The test `mazama_mobile/test/login_spec_store_test.dart:173` ("the shipped login spec is a usable sign-in spec") covers it.

**Not stored, logged or shown**
- `Session.toJson` (`mazama_mobile/lib/session.dart:69-74`) has no password field.
- A search for `password` in `lib/` finds only the places the claim lists (`main.dart`, `login_spec_store.dart`, `flow_runner.dart:28`, `debug_signin_files_page.dart`).
- No `print`/`debugPrint` touches it, and `defaultSecretKeys` (`flow_runner.dart:28`) scrubs it from errors.

**Caveats (all already stated in the claim)**
- A host added by a signed list can receive the POST.
- An answer to a question not marked secret is shown as it is typed.
- Values the state echoes back are not tracked.

### Claim 3: TRUE

- The step URL is checked as written (`flow_runner.dart:927`), then as built with `params` (`:930`), before `http.Request(...)..followRedirects = false` (`:933`).
- Each hop goes through `_nextHop` (`:841-846`), which checks both the raw `Location` and the resolved URL. A refused hop throws `_blocked` before sending (`:963-968`).
- Only GET/HEAD answered 301/302/303/307/308 are followed (`:818-827`), at most 10 hops (`:816`, `:958`).
- `hostAllowedUrl` (`flow_spec.dart:83-104`) requires https, refuses a backslash, an `@` in the authority or any port other than 443, applies a strict host grammar, and matches hosts exactly (defaults at `flow_spec.dart:73`).
- `_runOpenBrowser` checks `url`, the built start URL and `until` (`flow_runner.dart:769`, `778`, `779`).
- The claim's own exclusions (lab-report redirects to any https host with the `Referer`/`Origin`/`User-Agent` headers, `state_document_client.dart:70-74`, `94-98`; and the in-app browser) are accurate.

### Claim 4: PARTLY TRUE

**What holds**
- A fetched spec is held to `usableLoginSpec` (above) and to the allowlist at run time.
- The phone checks no signature on a spec. `login_spec_client.dart:62-101` has none.
- Host lists are used only through `verifiedHostList` (`mazama_mobile/lib/login_hosts_store.dart:90-98`), which wraps `verifySigned` (`mazama_mobile/lib/signing.dart:91-104`, with strict base64 and S < L).
- `HostList._` is private (`login_hosts_store.dart:81`). Lists only add exact hosts (`:39-44`, `:102-103`), and any list counts as newer than none (`:113`).
- `signing.pub` holds a 32-byte key and `hosts.json` lists no hosts (root, version `2026-10-25.1`).
- The new hosts are named only after the sign-in (`main.dart:641-650`) or under a failed retry (`main.dart:589`, `856-858`).
- The static check `_noStateApiRequests` (`login_spec_store.dart:165-175`) covers `request` and `open_browser` URLs at any depth, with vars filled in and a trailing dot or capitals normalised. The shared vectors include "the state's API host in other spelling".
- The runtime `neverRequest: {stateApiHost}` is passed on every sign-in (`sign_in_attempt.dart:32-33`) and renewal (`session.dart:210-212`). Every `runFlow('login'|'renew')` caller goes through those two functions (`main.dart:189`, `select_center_page.dart:248`, `319`, `cart_page.dart:865`, `1751`, `2391`, `debug_signin_files_page.dart:521-525`).
- The sale and read specs are never fetched (`state_client.dart:42`, `cart_page.dart:438`). Renewal always uses the password spec (`main.dart:748`, `_signedIn(session, widget.spec)`).

**What does not hold, by the claim's own wording**

1. **The in-app browser is part of a sign-in and can send to `psilocybin.oregon.gov`.**
   - `decideBrowserNavigation` (`mazama_mobile/lib/browser_sign_in_page.dart:77-82`) lets any main-frame URL on the allowlist load, and `psilocybin.oregon.gov` is on it (`flow_spec.dart:73`). Frames always load (`:80`), and sub-resources, XHR and Android POST navigations are never checked.
   - With the bundled spec, `until` is `https://psilocybin.oregon.gov/` (`mazama_mobile/assets/flows_phone/login_browser.yaml:77`, `:41`), so the code redirect is normally stopped. The `onPageStarted`/`onUrlChange` backstop (`browser_sign_in_page.dart:173-187`) admits that the state's page "may show for a moment first".
   - A fetched browser spec is checked only on its `open_browser` `url`, not its `params`. It can therefore keep `redirect_uri` on the state's site in `params` (`login_browser.yaml:66`) and choose a different `until`. B2C then sends the webview to `psilocybin.oregon.gov`, where it loads freely, and any other navigation to that host loads too.
   - So "while any sign-in or renewal runs, bundled specs included, nothing is sent to that host" (`SIGN-IN-SECURITY.md:158-161`) and the README's "refuses any request there while they run" (`README.md:24-26`) are not true of the browser sign-in. No app token is in the webview, and the app reads nothing but the final URL. The traffic is the webview's own, with the worker's fresh B2C session cookies.

2. **The runtime `neverRequest` misses a trailing-dot host.**
   - `_runRequest` compares `uri.host.toLowerCase()` (`flow_runner.dart:931`) and the redirect loop compares `next.host.toLowerCase()` (`:969`) against the set `{'psilocybin.oregon.gov'}`.
   - `hostAllowedUrl` strips one trailing dot before matching (`flow_spec.dart:92`), but Dart's `Uri` keeps it. A `Location: https://psilocybin.oregon.gov./…` answer from an allowed host therefore passes `_nextHop` and is followed.
   - The hop carries the step's own headers (except `Authorization`, dropped because the authority differs) and the run's cookies.
   - The static check catches the trailing dot in a spec's own URL. Only a redirect is exposed, and only an allowed host (the state's tenant, or a signed-list host) can send one, so the practical risk is low. Still, "a redirect there is not followed" is not unconditionally true.
   - The test `test/flow/flow_runner_test.dart:490-517` covers only the plain spelling.
   - I found this by reading the code, not by running it: there is no Dart toolchain here. Whether the TLS handshake would complete against a dotted name was not tested.

3. **"Never to read or change the worker's records" goes further than the code.**
   - The claim's "So a sign-in spec can use the worker's tokens only at the state's sign-in tenant (and a host a signed list added), never to read or change the worker's records" holds for requests made from the phone.
   - But a fetched spec may send the access and refresh tokens to a signed-list host (allowed by `specHostsAllowed` with `currentAllowedHosts`, `login_spec_store.dart:94`). Whoever runs that host can then call the state's API with them from anywhere.
   - The claim correctly says the phone sends nothing to the API. The conclusion holds only while no signed list adds a host.

**Smaller points**
- The bundled specs are not run through `usableLoginSpec` at start-up (`login_spec_store.dart:491`, `FlowSpec.fromYaml` only). That is consistent with the claim, which relies on tests for them.
- A fetched host list can be fetched and used for a retry before the worker sees it named (as stated).

## Other findings

1. **In-app browser and `psilocybin.oregon.gov`** (claim 4 point 1). This contradicts `SIGN-IN-SECURITY.md:158-161` and `README.md:23-26`. Fix in one line: either give `decideBrowserNavigation` `neverRequest` except for `until`, or scope the claim and README to "the app's own requests".

2. **Trailing-dot gap in the runtime guard** (`flow_runner.dart:931`, `969`, against `flow_spec.dart:92`). Fix in one line: compare the host with one trailing dot stripped, as `urlHostForSecrets` does.

3. **README overstates the promise.**
   - `README.md:12-13` says the password and tokens "are never sent to Mazama or anyone else", and `README.md:18` says the steps "can only post the password ... never to Mazama". Both are promises about intent, not mechanisms. The signing key's holder, which `SIGN-IN-SECURITY.md:335-337` says is kept in the server's encrypted secrets (so anyone who takes over the server has it too), can sign a list adding any host. A fetched spec can then post the password, and send the email and tokens, to that host. The phone names the host only after the post (`main.dart:641-650`).
   - `README.md:26`, "Sign-in steps can't read or change a worker's records, whoever wrote them", has the same limit (claim 4 point 3).
   - The claims document says this under "What these claims do not cover". The README summary should say it plainly too.

4. **A fetched spec controls where the email and tokens go at the sign-in hosts**, including in URLs and queries. Those then reach the state's tenant logs, or a signed-list host's logs. Claim 4 states this; claim 2's "Where to look" lists only the bundled specs, and should point to claim 4.

5. **Shared webview storage.** The B2C session cookies the worker gets on the state's page live in the app-wide webview storage until the clearing at close, which is best effort and doesn't run if the app is killed. In that window the inventory portal (`inventory_portal_page.dart:30`, JavaScript on, no host filter, Mazama's own site) shares the same cookie store. Same-origin rules keep its page from reading the state's pages, so I found no way to exfiltrate data. A careful reader may still want to know.

6. **Data that leaves the phone outside the claims, all already disclosed elsewhere:**
   - lab-report downloads follow a redirect to any https host with `Referer`/`Origin`/`User-Agent` (claim 3);
   - the label photo goes to whichever camera app is installed (claim 8);
   - ML Kit usage metrics go to Google (claim 8);
   - server-chosen product-sheet links (`sheets_client.dart:114`, `mazama_inventory_client.dart:57`) open in an in-app browser tab;
   - the share sheet sends the reconciliation image with the email (`reconcile_page.dart:139`, `341`);
   - in debug builds only, the Sign-in files page fetches from a typed https address (`debug_signin_files_page.dart:69-93`).
