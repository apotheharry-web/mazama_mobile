# Independent audit of `mazama_mobile/SIGN-IN-SECURITY.md` (audit copy 4)

## Summary

I checked the nine claims against the Dart source, the bundled flow specs, and the Android and iOS native code and
settings. I did not rely on comments. In this source, the password goes only into a form field of a POST to a host
other than `psilocybin.oregon.gov`. Tokens go only to allowlisted hosts and never to Mazama's server. Every flow
request and redirect hop is checked against the allowlist. Host lists must carry a valid signature. Failure reports
carry fixed fields only. The session file is excluded from backups.

The one material problem is claim 4. It says no sign-in spec can make a request to `psilocybin.oregon.gov`, and the
README repeats this as "sign-in steps may never talk to the state's main system". The phone checks only `request`
steps for this. Two things get past that check. First, a browser spec's `open_browser` step may open
`psilocybin.oregon.gov`, and the bundled spec's `until` is on that host. Second, a GET or HEAD sign-in request is
followed through redirects to `psilocybin.oregon.gov`. On such a hop only `Authorization`, `Cookie`, `Host` and
`Content-*` are dropped. Any other header the spec sets, including one carrying `{{access_token}}` or
`{{refresh_token}}`, goes with it, and so do the run's B2C cookies. This applies to the unattended `renew` flow and to
the bundled `authorize` step, which keeps the default `follow_redirects: true`. So "never read or change the worker's
records" is not enforced by the phone. It holds only as long as B2C does not redirect there, or the state's API
accepts tokens only in `Authorization`.

The other documents have smaller errors. Claim 2's sentence about cookies is wrong, for the same redirect reason.
Claim 4 says every saved fetched spec renews the session, but a saved browser spec never does. Claim 7 says every
server request carries the center id, which is not so. The README's headline promise doesn't mention the signed host
list.

## Per-claim evidence

### Claim 1: TRUE

- **Where the password comes from:** it is read once into the `inputs` map at `mazama_mobile/lib/main.dart:541` and
  passed to `_attempt` (`main.dart:550`, retry `main.dart:580`). From there it goes to `attemptSignIn` →
  `runFlow(spec, 'login', inputs, …)` (`mazama_mobile/lib/sign_in_attempt.dart:30`). The demo check at
  `main.dart:56,533` sends nothing.
- **Other uses in `lib/`:** a search for `password` finds only `main.dart` (the field at :843-849, :541),
  `flow/flow_runner.dart:28` (secret keys), `login_spec_store.dart:32,113,137`, and the debug-only
  `debug_signin_files_page.dart:501-523,668-701`. That page is reachable only under `kDebugMode`
  (`select_center_page.dart:463`) and calls the same `attemptSignIn`.
- **The rule is enforced in code.** `usableLoginSpec` (`mazama_mobile/lib/login_spec_store.dart:79-110`) runs these
  checks:
  - `_secretsPlaced` (:194-233): `{{password}}` and every `await_input` answer may appear only as the exact value of a
    `form` field (:157). The step must be `type: request` with `method` exactly `POST` (:152), and the URL host,
    filled in from vars, must not be `psilocybin.oregon.gov` (:153-154).
  - The scan for the template covers resolved `vars`, flow names and every step key and value (:199-212).
  - No `when` or `json_var` may name the password, email, refresh token or an answer (:216-221), and no check `vars`
    may name a typed value (:222-229).
  - No var may be named `email`, `password` or `refresh_token` (:195).
  - `_plainMapsOk` (:240-254) and `_setNamesOk` (:277-289) close the remaining gaps.
- **Every non-bundled spec is checked:** a saved spec (`login_spec_store.dart:472,520`), a fetched spec
  (`login_spec_client.dart:94`, and again at `main.dart:568-572` and `main.dart:721-723`), and the browser spec
  (`browser_login_spec.dart:24-26`).
- **Bundled spec:** the password appears only in `self_asserted`, a POST to the B2C tenant
  (`mazama_mobile/assets/flows/login.yaml:85-98`).
- **Redirects:** a POST is never followed (`flow_runner.dart:821-822,949`), so the password cannot be carried on to
  another host.
- **Not stored:** `Session.toJson` has no password field (`mazama_mobile/lib/session.dart:68-73`).
- **Not logged:** no `print` or `debugPrint` in `lib/` takes sign-in data (see the search under Method).
- **Caveat (low):** the rule limits where `{{name}}` is written in the spec text. `_fail` replaces `{status}` with
  the HTTP status *before* it fills in templates (`flow_runner.dart:201-202`). So the text `{{a{status}}}` becomes
  `{{a401}}` after the scan. This lets a spec put the answer to a question named `a401` (or any name ending in digits)
  into an error message, although the rule says answers may appear only in a POST form field. It cannot form
  `{{password}}`. Secret answers are still scrubbed (`flow_runner.dart:700`), and sign-in errors are shown only on the
  phone, so nothing leaves the device.

### Claim 2: TRUE (with one inaccurate supporting sentence)

- **Bundled flows:** every `Authorization: Bearer {{access_token}}` is on `{{api}}` = `https://psilocybin.oregon.gov/…`
  (`assets/flows/state_reads.yaml:40-42,55-57,80-82,105-107,130-132`; `sale.yaml:28-41`; `sb303.yaml:21-36,60-62`).
  The `refresh_token` form field goes only to the B2C token endpoint (`login.yaml:174-183`,
  `flows_phone/login_browser.yaml:137-146`).
- **Flow requests:** all of them run through `runFlow` with `currentAllowedHosts()`
  (`state_client.dart:72`, `cart_page.dart:1771,2407`, `session.dart:209`).
- **Redirects in flows:** a hop to another authority drops `Authorization` (`flow_runner.dart:858,862`).
- **Lab-report downloads:** the first host is checked (`state_document_client.dart:62`). The token is added only for
  the same scheme, host and port (:66,75). Redirects must be https but may go to any host (:95).
- **Mazama clients:** all 16 clients that use `appApiKeyHeaders` were read. None puts `accessToken`, `refreshToken`
  or `Bearer` in a request. The app key is a build-time constant (`app_api_key.dart`).
- **Lab-report upload:** `configured_coa_submit.dart:74-96` reads from the state with the token and uploads only the
  guid, PDF, doc id, email, device id and state psilocybin figure (`coa_data_client.dart:212-222`). The catch-up path
  keeps no token on disk (`catch_up_store.dart:38-44,70-76`); it reads the token from `session.json` when it sends
  (`server_link.dart:213-217`).
- **Caveat (inaccurate sentence):** the doc says "the sign-in makes no request to psilocybin.oregon.gov … so the
  state's B2C session cookies go only to B2C" (`SIGN-IN-SECURITY.md:113-116`). That is not what the code does.
  - The cookie jar is not scoped by host (`flow_runner.dart:687,865-866`).
  - GET requests in sign-in steps follow redirects to any allowed host (`flow_runner.dart:918,949-962`).
  - The bundled `authorize` step has no `follow_redirects: false` (`login.yaml:47-64`). If B2C answers it with a
    redirect to `redirect_uri` (`https://psilocybin.oregon.gov/`, `login.yaml:28-30`, for example to report an
    error), the phone sends a GET to `psilocybin.oregon.gov` carrying the B2C cookies.
  - The cookies still stay within the allowlist, so the claim itself stands.
- **Note:** spec-set headers other than `Authorization` survive a cross-host hop (`flow_runner.dart:851,859-864`).
  This is still within the allowlist.

### Claim 3: TRUE

- **Allowlist and check:** `defaultAllowedHosts` (`flow/flow_spec.dart:73`) and `hostAllowedUrl` (:83-104) require
  https, port 443 if written, no `\` or `@`, a strict host shape, and an exact match.
- **Requests:** `_runRequest` checks the URL as written and again after params are added (`flow_runner.dart:921,924`).
  The request is built with `followRedirects = false` (:926).
- **Redirect hops:** each is checked by `_nextHop` (:836-841, used at :956). The hop request is rebuilt with
  `followRedirects = false` (:857). Only GET and HEAD with 301/302/303/307/308 are followed, at most 10 times
  (:810-822).
- **Open-browser start URL:** checked before `browse` is called (:764,773-774).
- **Static check:** `specHostsAllowed` checks every `request` and `open_browser` URL after filling in vars
  (`flow_spec.dart:141-156`).
- **Host cannot change at run time:** a host containing `{{` fails the check, and `_setNamesOk` stops any step from
  setting a var.
- **Stated exception:** the doc's "Not covered" note on downloads matches `state_document_client.dart:70-98`.

### Claim 4: PARTLY TRUE

What holds:

- A fetched host list counts only through `verifiedHostList`, which runs Ed25519 verification with a strict base64
  and S<L check (`login_hosts_store.dart:90-95`, `signing.dart:71-75,90-101`). `HostList._` is private (:81).
- A saved list is verified again when loaded (:153-161), and a list only adds hosts (:102-103).
- `signing.pub` holds a 32-byte key (`assets/signing/signing.pub`). The root `hosts.json` adds no hosts.
- The hosts a list adds are announced only after a successful sign-in (`main.dart:641-650`).
- A phone that has no list accepts any validly signed list (`login_hosts_store.dart:113`).
- The phone does not check a signature on a fetched spec; it applies the rules (`login_spec_client.dart:94`).
- The sale and read specs are bundled only (`cart_page.dart:438`, `state_client.dart:42`).

What does not hold as written ("no sign-in spec … may have a request to psilocybin.oregon.gov … never to read or
change the worker's records", `SIGN-IN-SECURITY.md:150-157`; README :23-25):

1. **`open_browser` is not checked.** `_noStateApiRequests` checks only nodes with `type == 'request'`
   (`login_spec_store.dart:165-175`, specifically :167).
   - An `open_browser` step's `url` and `until` only have to pass the general allowlist (`flow_spec.dart:148`), which
     includes `psilocybin.oregon.gov`.
   - So a fetched or saved browser spec may open the state's site in the webview. The bundled spec's `until` is
     already on that host (`flows_phone/login_browser.yaml:39-41,77`).
   - The shared cases include no "open_browser to the state's API" refusal
     (`assets/shared/flows/contracts/login_spec_validity.json`).
   - The webview gets no app token and its storage is cleared before it opens, so this is a wording gap, not a token
     leak.
   - The webview code itself says the state's site "may show for a moment" when a redirect bypasses the navigation
     delegate (`browser_sign_in_page.dart:169-183`).
2. **Redirect hops are not checked against the API host.**
   - Any GET or HEAD step in `login` or `renew` follows a redirect to any allowed host, including
     `psilocybin.oregon.gov` (`flow_runner.dart:918,949-962`). `renew` runs unattended at start-up and before every
     sale (`main.dart:189`, `cart_page.dart:1751`).
   - `_hopRequest` drops only `host`, `cookie`, `content-*`, and `authorization` on another host
     (`flow_runner.dart:851-864`). A spec header such as `X-Token: {{access_token}}` or `{{refresh_token}}` goes on to
     the state's host, and so does the run's cookie jar.
   - The spec controls the parameters of its B2C request, so where B2C redirects is partly up to the spec. The phone
     does not check this.
   - So "can use the worker's tokens only at the sign-in tenant … never to read the worker's records" depends on
     B2C's redirect behaviour and on the state's API ignoring anything but `Authorization`. The claim does mention
     redirects, at :158-159, but says only that `Authorization` is dropped.
3. **Not every saved fetched spec renews.** The claim says "a fetched spec that signs in is saved and from then on
   runs the session's renewal". That is true only for the password spec. A fetched browser spec is saved
   (`main.dart:742-747`), but the session renews with `widget.spec` (`main.dart:748`), so the browser spec's `renew`
   never runs.

### Claim 5: TRUE (within its stated limits)

- **No JavaScript in or out:** there is no `runJavaScript`, `addJavaScriptChannel`, `JavaScriptChannel` or
  `evaluateJavascript` anywhere in `lib/` (search below). JavaScript is on (`browser_sign_in_page.dart:165`).
- **Navigation rule:** `decideBrowserNavigation` handles `until` first, then the allowlist for the main frame, and

- **Caveat:** in the `onPageStarted`/`onUrlChange` backstop path, the `until` page (the state's site) may actually

## Other findings

1. **README promise (`README.md:12-14`):** "the state's sign-in tokens go only to the state" has no qualifier. With a
   list signed by the owner's key, the password and tokens can go to any host the key holder signs (claims 1, 2
   and 4). The README mentions this only later, in passing (:18-21).
2. **README :23-25:** "sign-in steps may never talk to the state's main system … can't read or change a worker's
   records, whoever wrote them" overstates what the phone enforces (see claim 4, items 1-2). It also says saved
   steps "renew the worker's session", which is not true of saved browser specs (claim 4, item 3).
3. **Missing from "What these claims do not cover":**
   - Redirect hops carry spec-set headers other than `Authorization`, and the run's cookies, to any allowed host,
     including `psilocybin.oregon.gov`.
   - The state's site may load in the sign-in webview at the end of a sign-in.
4. **Rule evasion through `{status}` (`flow_runner.dart:201-202`):** see claim 1. It has no effect off the phone. One
   line fix: fill in templates before replacing `{status}`, or refuse `{status}` next to `{{`.
5. **Suggested one-line fixes:**
   - Claim 4 / `_noStateApiRequests`: also apply it to `open_browser` `url`.
   - Claim 4: follow no redirect, or none to `psilocybin.oregon.gov`, in sign-in flows.
   - Claim 4: drop every spec-set header on a cross-host hop, not only `Authorization`.
6. **Nothing else found that sends user data off the phone** beyond the claims and the "do not cover" list:
   - the Dart default `User-Agent` on server requests (platform and Dart version);
   - the camera app chosen for ACTION_IMAGE_CAPTURE;
   - `share_plus` targets the worker chooses;
   - links opened by url_launcher;
   - the inventory portal webview;
   - ML Kit telemetry.
