# Audit of `mazama_mobile/SIGN-IN-SECURITY.md` against the source

## Summary

I checked the nine claims against the Dart code, the bundled flow specs and the Android and iOS native code. I relied on the code, not the comments. I found no path that sends the password, an access token or a refresh token to Mazama's server, or to any host off the app's allowlist. The password rule in `usableLoginSpec` holds against every bypass I tried: nested values, keys, var concatenation, re-templating, redirects, method case, host-through-var and runtime host changes. All flow requests and redirect hops are checked against the allowlist before they are sent. Host lists are Ed25519-verified against a real bundled key. Error messages are scrubbed as described. Backups are turned off on Android and excluded on iOS. Seven claims hold as worded, each with minor caveats. Claim 7 is accurate in everything it lists, but its list of data sent to Mazama is incomplete. The most important omission is in claim 4 and the README, not in the code: a sign-in spec fetched from Mazama's server is saved after it signs in. It then runs unattended on every launch and every token renewal. Within the allowlist, it can send any request to the state's API with the worker's tokens, writes included. The documents describe Mazama's power as "choosing sign-in steps", which understates this.

## Claim 1: The password goes only to the state's sign-in, as a form field of a POST

**Evidence**
- The password enters at `mazama_mobile/lib/main.dart:843-849` (`obscureText: true`). It is placed in `inputs` at `main.dart:541` and passed only to `_attempt` (`main.dart:550`, retry `main.dart:580`). `_attempt` calls `attemptSignIn` (`main.dart:772-775`), and that calls only `runFlow` (`mazama_mobile/lib/sign_in_attempt.dart:30`). `runFlow`'s returned context (which still holds the password) is read only for tokens (`sign_in_attempt.dart:37`, `mazama_mobile/lib/session.dart:102-115`) and then dropped.
- The demo check `isDemoSignIn` is local (`main.dart:56`, `main.dart:533-536`).
- Nothing saves it: `Session.toJson` has `access_token`, `refresh_token`, `email`, `expires_at_ms` only (`session.dart:68-73`).
- Nothing prints it. `print(`/`debugPrint(` never touch `inputs`, and the catch-alls show only `${e.runtimeType}` (`main.dart:602-605`, `sign_in_attempt.dart:33-34`).
- The rule (`mazama_mobile/lib/login_spec_store.dart`):
  - No var may be named `email`, `password` or `refresh_token`: `:177`.
  - `{{password}}` and every `await_input` answer (`typedNames`, `:134-143`) are searched in var keys and values, flow names and every step key and value at any depth (`:181-195`, `_hasText` `:160-165`).
  - It is allowed only as the exact value of a `form` field when `type == 'request'` and `method == 'POST'` (exact case), and the host filled in with `vars` is not `psilocybin.oregon.gov` (`_typedFormFields` `:148-157`; `urlHostForSecrets` lower-cases and strips the port and trailing dot, `:120-130`).
  - No `when`/`json_var` may name a typed name, `email` or `refresh_token`, and no check `vars` may name a typed name (`:198-213`).
  - Plain-text maps with no `{{` in keys: `_plainMapsOk` `:222-236`.
  - No step may overwrite a var or a flow input (renew's `refresh_token` extract excepted): `_setNamesOk` `:259-271`.
  - Templates are exactly `\{\{(\w+)\}\}`, single-pass (`mazama_mobile/lib/flow/flow_spec.dart:16-26`). A var that builds the literal text `{{password}}` is therefore never expanded again.
  - Only `format`, `vars` and `flows` are read (`flow_spec.dart:213-235`).
- Where the rule runs:
  - saved specs: `login_spec_store.dart:451-460`, `:501-502`;
  - fetched specs: `mazama_mobile/lib/login_spec_client.dart:94`, re-checked at `main.dart:569-572` and `main.dart:721-723`;
  - the bundled browser spec: `mazama_mobile/lib/browser_login_spec.dart:24`.
  - The bundled `login.yaml` is not checked at run time (`login_spec_store.dart:473`). As the claim says, it is covered by the test `'the shipped login spec is a usable sign-in spec'` (`mazama_mobile/test/login_spec_store_test.dart:172`).
- The interpreter keeps to the rule:
  - The POST body comes from `form` (`mazama_mobile/lib/flow/flow_runner.dart:932-937`).
  - POSTs are never redirected (`redirectRules`, `flow_runner.dart:821-822`, applied `:949`).
  - Hosts are checked before sending (`:921-924`).
- `mazama_mobile/assets/flows/login.yaml:85-98`: the only `{{password}}` is `self_asserted`, a POST to `{{b2c}}/{{pol}}/SelfAsserted`. Its host comes from the var `b2c`, which is the tenant.
- The shared vectors include the cases named in the claim (`mazama_mobile/assets/shared/flows/contracts/login_spec_validity.json`: "password in a url path", "a var named refresh_token", "password posted to the sign-in tenant", "renew extracts the rotated refresh_token", etc.).
- The `password` search finds only the places the claim lists: `main.dart`, `login_spec_store.dart`, `flow_runner.dart:28`, `debug_signin_files_page.dart`.

**Caveats (all stated in the claim)**
- A host added by a signed list may receive the POST.
- A non-secret answer is shown and not scrubbed.
- Values a host echoes back aren't covered.
- The rule does not cover the email at all: the email may go in any URL, header or form to any allowed host, `psilocybin.oregon.gov` included. The claim doesn't say otherwise.

## Claim 2: Tokens go only to the allowlisted hosts (today, the state's)

**Evidence**
- The bundled flows put `Bearer {{access_token}}` only on `{{api}}` = `https://psilocybin.oregon.gov/api/private/ProductTracking/`:
  - `mazama_mobile/assets/flows/state_reads.yaml:40-42, 55-57, 80-82, 105-107, 130-132`;
  - `sale.yaml:28-41`;
  - `sb303.yaml:21-36` (unused: no `sb303` reference in `lib/`).
- The bundled flows put `refresh_token` only in a form to `{{b2c}}/…/token` (`login.yaml:173-183`, `assets/flows_phone/login_browser.yaml:136-146`).
- Every token-carrying flow run passes the current allowlist:
  - state reads: `mazama_mobile/lib/state_client.dart:72-73`;
  - sale: `mazama_mobile/lib/cart_page.dart:1771-1772`, `:2407-2408`;
  - renewal: `session.dart:209-210`.
- `downloadStateDocument` (`mazama_mobile/lib/state_document_client.dart`):
  - The first URL must pass `hostAllowedUrl` (`:62-64`).
  - It follows redirects itself (`:70-71`, `:83-98`) and sends `Authorization` only when the scheme, host and port equal the first URL's (`:66`, `:75`).
- Cross-host flow hops drop `Authorization` (`flow_runner.dart:856-868`; Dart's `Uri.authority` omits the default port, so `:443` is not a different authority).
- Mazama clients send only `appApiKeyHeaders` and JSON/multipart bodies. Grepping each file that uses `appApiKeyHeaders` for `accessToken|refreshToken|Bearer|access_token` finds only a comment (`sale_log_client.dart`).
- `configured_coa_submit.dart:74-96` and `coa_data_resolver.dart:174-186` use the token only for state calls, then upload bytes, guid, doc id, email, device id and psilocybin (`coa_data_client.dart:210-222`).
- Catch-up work does not keep the token on disk. It reads it from `session.json` at send time (`catch_up_store.dart:38-44`, `server_link.dart:213-217`).

**Caveats**
- The cookie paragraph is stronger than the current behaviour. It says "during sign-in the state's B2C session cookies also go to `psilocybin.oregon.gov`". But no bundled `login` step requests that host:
  - all requests go to `{{b2c}}…`;
  - `confirmed` does not follow the redirect to the site (`login.yaml:126-131`);
  - each `runFlow` has its own jar (`flow_runner.dart:687`).
  
  It is true only for a spec that makes such a request. It is still true that the jar is not scoped by host (`flow_runner.dart:299-302`, `:929-930`, `:865-866`).
- Cross-host hops drop only `Authorization`. A spec that puts a token in another header (e.g. `X-Token`) keeps it across hosts, though still only on allowed hosts.

## Claim 3: Every request the sign-in and state flows make is held to the host allowlist, redirects included

**Evidence**
- `defaultAllowedHosts` is the two exact hosts (`flow_spec.dart:73`). The check (`flow_spec.dart:83-104`) requires https, refuses `\` and `@`, allows only port 443, and requires a host made of `[A-Za-z0-9-]` labels.
- `_runRequest` checks the URL as written and the built URL (`flow_runner.dart:921-924`), and builds with `followRedirects = false` (`:926`).
- The redirect loop follows only if `redirectRules` allows it (GET/HEAD and 301/302/303/307/308, `:813-822`). Each hop goes through `_nextHop` (absolute, scheme-relative and resolved forms all checked, `:836-841`) before it is sent (`:956-962`). At most 10 hops (`:811`, `:951-955`).
- A refusal is `_blocked` and nothing is sent (`:827-829`).
- `open_browser` start URL and `until` are checked (`:764-774`).
- I found no parse gap between the text check and `Uri.parse` (the authority ends at `/?#` in both).

**Caveats**
- Already listed under "Not covered": a document download may be redirected to any https host (up to 5 hops). The `Referer`, `Origin` and `User-Agent` headers and the doc id in the path go there (`state_document_client.dart:70-74`, `:94-98`).
- The debug-only `fetchHostedFile` (`debug_signin_files_page.dart:81-93`) is not a flow and fetches any https address typed into it, as the document says.

## Claim 4: Mazama's server is trusted for sign-in only within these rules

**Evidence**
- Fetches happen only after a failed sign-in:
  - password path: `main.dart:551-568` (not for `credentials`/`cancelled`, `:554-557`);
  - browser path: `main.dart:712-718` (after any failure).
- A fetched spec must pass `usableLoginSpec` under the attempt's hosts (`login_spec_client.dart:94-97`, again at `main.dart:569-575`). Its version must be newer than the one that failed (`main.dart:570`, `:721`). There is no signature check on the phone.
- Host lists are used only if `verifiedHostList` succeeds:
  - `login_hosts_client.dart:77-95` and `login_hosts_store.dart:90-98`, re-verified on load at `:153-165`;
  - `signing.dart:91-104`: strict base64, S < L, `Ed25519().verify`.
- Lists only add hosts (`login_hosts_store.dart:102-103`). `HostList._` is private (`:81`).
- `assets/signing/signing.pub` holds a 32-byte key (`wRJ0Vw+q+ERwZZdPNLr3M6tx+E7F9eZUMgff5Tfu7ps=`), not `none`.
- New hosts are named only after success (`main.dart:641-650`, `:268`) or under a failed retry (`main.dart:589`, `:271`).
- "Can't be withdrawn from a phone that has none in use": `newerHostList(candidate, null)` is always true for a valid version, and `onlyRemovesHosts` is false when nothing is in use (`login_hosts_store.dart:113-123`).

**Caveats (missing from the claim and the README)**
- A fetched spec that signs in is saved (`main.dart:634-639`). From then on it is the spec of every renewal:
  - at every launch (`main.dart:136-139`, `:184-190`);
  - before every sale (`cart_page.dart:1751`, `:2391`);
  - on the page timers.
  
  Renewal runs with no person present.
- A spec's `login` and `renew` flows may contain any number of request steps to `psilocybin.oregon.gov`. They may carry `Bearer {{access_token}}`, and `{{refresh_token}}`/`{{email}}` in URLs, params, headers or form fields. Only `when`/`json_var` are barred from naming them.
- So, within the allowlist, Mazama's server (or anyone answering as it) can have the phone make any state-API request as the worker, writes included, at sign-in and silently at every renewal. Two examples: a POST to a write endpoint with the refresh token as a form field, or GETs whose URLs carry the token into the state's logs.
- Whether Mazama could read such data back depends on the state system and is not established by this source. The claim's phrase "chooses … where on the allowed hosts the email and tokens go" logically covers this, but "trusted for sign-in only" and the README's "sign-in steps" suggest much less.

## Claim 5: Signing in on the state's own page: the app does not read what the worker types

**Evidence**
- `mazama_mobile/lib/browser_sign_in_page.dart:164-202`: JavaScript on, a `NavigationDelegate`, and nothing else. No `runJavaScript`, `addJavaScriptChannel`, `JavaScriptChannel`, `evaluateJavascript` or `getCookies` anywhere in `lib/`, `android/` or `ios/` (searched).
- `decideBrowserNavigation` (`:77-82`):
  - `until` comes first (main frame: finish, never loaded; frame: prevent);
  - frames navigate unchecked;
  - main frames go through `hostAllowedUrl` with the flow's own hosts (`:240-253`; the hosts are passed in from `main.dart:711`, `:731`, `:761-767`).
- The returned URL goes only to the `open_browser` extracts and `then_require` (`flow_runner.dart:779-791`). The errors there are fixed texts. The code is exchanged at `login_browser.yaml:108-119`.
- Clearing:
  - before load: `_start` awaits `_clearSiteData` (`browser_sign_in_page.dart:207-211`), which calls `WebViewCookieManager().clearCookies()`, `clearCache()` and `clearLocalStorage()` (`:226-230`). Failures are ignored (`:86-94`).
  - best effort on `dispose` (`:264-268`).
- The inventory portal webview has JS on and no navigation restriction (`mazama_mobile/lib/inventory_portal_page.dart:29-56`). It is given no token.

**Caveats**
- The app does see every navigation URL the page starts (`onNavigationRequest`, `onPageStarted`, `onUrlChange`, `:166-187`). It uses them only to decide, keeps none and sends none. "Reads only the address the page finally goes to" is loose wording.
- "Site data" means exactly those three plugin calls. Whether they also clear IndexedDB, sessionStorage or service-worker data (especially on iOS) depends on `webview_flutter_*`, which is not in this copy and could not be verified.
- What Android's WebView routes through the delegate (POSTs, redirects, frames) is plugin and OS behaviour, as the claim itself says. The source logic matches the claim.

## Claim 6: Secrets are scrubbed from error messages

**Evidence**
- `defaultSecretKeys` (`flow_runner.dart:28`). `_scrub` does a case-insensitive exact-value replace of each key's current value (`:145-153`).
- `_scrub` is applied:
  - in `_fail` (`:198-206`), which builds every check error (`:240-241`), every transport error (`:884-900`), redirect overflow (`:953-954`) and `_blocked` (`:827-829`);
  - to `await_input` prompts (`:740`).
- Secret answers are added to the scrubbed keys (`:700`).
- Interpreter messages about spec settings name only spec fields or nothing (`:86`, `:236`, `:255-256`, `:437-443`, `:472`, `:521`, `:548`, `:651`, `:704`, `:806`).
- `open_browser` errors never contain the returned URL (`:775-784`).
- Bundled browser-spec errors don't name `code` (`login_browser.yaml:87`, `:98`, `:106`, `:124`, `:134`).
- Session problems in failed-sale reports use fixed texts:
  - `sessionFailureReportText` (`session.dart:158-163`);
  - used at `cart_page.dart:1828`, `:1840`, `:2421`, `:2427`.
- The only `FlowError.message` sent to the server is the bundled sale flow's (`cart_page.dart:1857`, `:2433`; spec from `rootBundle` at `cart_page.dart:438`).
- Sign-in failure reports carry no message (`signin_failure_client.dart:107-114`).

**Caveats (as stated in the claim)**
- Encoded copies, values held under other names, and the email in browser, renew and read runs are not scrubbed.
- Scrubbing replaces in key order (password, email, tokens). A secret that contains an earlier secret as a substring would be only partly masked. This is theoretical for real values.
- Release builds write some error text to the device log (Known gaps).

## Claim 9: Where credentials and tokens are stored on the phone

**Evidence**

- Android:
  - `allowBackup="false"` and `fullBackupContent="false"` (`android/app/src/main/AndroidManifest.xml:13-14`);

- The email is also in:
  - `server_outbox.json` (`lib/server_outbox.dart:110-123`);
  - `server_catch_up.json` snapshots (`lib/catch_up_store.dart:70-76`; lots carry no email).

- The report image goes to the temporary folder (`reconcile_page.dart:135-137`). Scan photos go to the cache folder (`TextScanner.kt:74`).
- The iOS widget uses the app group (`ios/Runner/Runner.entitlements`, `CartTimerWidget.swift:22`). Its snapshot holds cart names, timers and the center name, but no email or token (`lib/cart_timer_widget.dart` `cartTimerSnapshot`).

**Caveats**
- `debug_local_storage_page.dart:69-73` shows the email, the expiry and only whether tokens are present. It does not show the file or the token values, so the claim overstates (harmlessly).
- On iOS, WKWebView cookies and site data are kept under `Library/` outside Application Support, which iOS includes in backups by default (to my knowledge; not visible in this source). The state page's cookies would be in a backup only if the after-close clearing didn't happen (app killed mid sign-in). The inventory portal's cookies can be in one at any time.

## Other findings

1. **Biggest disclosure gap (claim 4, README).** A server-fetched sign-in spec that has signed in once is saved and becomes the renewal spec. It runs at every launch and before every sale with no person present. It can make any request the allowlist permits with the worker's tokens and email, including writes to the state API as the worker (`login_spec_store.dart:176-215` bars only `when`/`json_var`/checks, not request fields, from naming the tokens; `main.dart:634-639`; `session.dart:209`). The README describes this as "newer sign-in steps" that "can only talk to the state's addresses". Fix: say plainly in claim 4 and in the README that a fetched spec can act on the state system as the worker, unattended, until a newer bundled spec replaces it.
2. **Claim 7 is incomplete.** It leaves out `/p/coa-data/batch` (`coa_data_client.dart:129-152`, all lot ids of an unconfigured center), the `doc_id`/`state_psilocybin` upload fields (`coa_data_client.dart:221-222`), and the center id in every `/p/` path (`api_contract.g.dart:7-33`). Fix: add them to the "Business data" bullet.
3. **The claim 2 cookie paragraph overstates current behaviour.** With the bundled specs, no sign-in request goes to `psilocybin.oregon.gov` (`login.yaml:47-171`; `confirmed` uses `follow_redirects: false`, `:131`), and each flow run has its own jar (`flow_runner.dart:687`). Fix: say "would go … if a spec requested that host".
4. **Claim 9, debug page.** It shows a summary, not the file (`debug_local_storage_page.dart:69-73`). Fix: reword.
